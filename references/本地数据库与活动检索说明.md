# 本地数据库和历史活动查找

## 数据已经保存在哪里

文章都保存在 `data/articles.sqlite3`。这是一个本地数据库文件：程序在后台读写它，你可以用 Excel 清单或聊天页面查看内容，不用直接打开这个文件，也不用学习 SQL。

当前有三类记录：

| 记录 | 可以把它理解成 | 里面有什么 |
|---|---|---|
| `articles` | 文章档案 | 标题、公众号、作者、发布时间、原文链接、正文文字、保留排版的 HTML、导入状态 |
| `article_images` | 文章配图清单 | 每张图属于哪篇文章、原始图片地址、本地图片路径、下载状态 |
| `import_jobs` | 导入流水 | 什么时候导入哪个链接、是否成功、失败原因 |

每篇文章可以有很多张图，所以一条文章档案会对应多条图片记录。导入流水只是记录操作过程，不是文章正文。

## 现在怎么查以前的活动

当前这 10 条数据是“公众号文章”，还没有单独整理成“活动档案”。聊天助手会先按问题里的关键词搜索标题和正文，选出相关度较高的文章，把摘要和原文链接交给模型，再用这些文章回答。回答下方会附上来源，方便打开原文核对。

比如问“之前有哪些新生迎新活动”，系统会在文章标题和正文中找“新生”“迎新”等相近关键词。文章发布时间代表公众号发文时间，不能自动当成活动举办日期；预告或报名推送也不能当成活动已经顺利举办的证明。

本版用中文词组和相邻字词进行本地匹配，10 篇文章的规模不需要额外安装搜索服务。它擅长找到用词相近的文章；如果活动叫法完全不同，可能漏掉同义表达。只有图片、没有可提取正文文字的文章，也只能按标题搜索。

## 后续如何变成“活动档案”

文章和活动是两回事。一场活动可能有预热、报名、回顾多篇文章，也可能还有问卷结果、预算和实际人数。下一步扩展时建议增加两类资料：

- **活动档案**：活动名称、类型、实际举办日期、面向对象、报名人数、到场人数、满意度、复盘结论。
- **文章和活动的关联**：把每篇推送关联到活动，并标记它是预热、报名、回顾或总结。

这样问“以前的迎新活动到场情况如何”，助手就能先找活动档案，再打开对应的报名稿和回顾稿。AI 可以先提出文章归属和活动信息建议，由人确认后写入档案；未经确认的推断应保持为建议，避免把推文发布时间错当成活动日期。

## 聊天时数据如何流动

```text
你在本机网页输入问题
        ↓
本机 API 在文章库里找相关推送
        ↓
将问题和命中的文章片段发给 GPT-6 Sol（推理强度 high；接口临时不可用时尝试备用模型）
        ↓
网页显示回答，并列出参考原文
```

API 密钥保存在本机 `.env` 文件，只由后端读取，不会发送给浏览器。当前模型请求通过 Aizex Codex API 发出；为了让模型回答，问题以及命中的文章标题、发布时间、链接和正文片段会发送到 Aizex。未命中的整库内容不会随每次提问一并发送。
